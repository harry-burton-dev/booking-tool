# palint.config.json change (proposed)

Generated by the overnight SAFE fix batch (2026-07-31), theme 1 (markers). Do not apply directly —
this describes the exact change for a human/orchestrator to make to the real
`palint.config.json` at the repo root, once the `// RESET-SITE[...]` markers added in this batch
have been reviewed. Not applied to the real config; L6 stays vacuous (`statefulVars: []`) until
someone makes this edit deliberately, per H-3 (code-review 20260731).

## Change

In `palint.config.json`, replace:

```json
  "statefulVars": [],
```

with:

```json
  "statefulVars": [
    "varSelectedRoom",
    "varSelectedDate",
    "varStartTime",
    "varEndTime",
    "varTitle",
    "varConflict",
    "varBookingError",
    "varSubmitting",
    "varTitleTouched",
    "varConflictingBooking",
    "varNextFreeSlot",
    "gblEditingBookingID",
    "gbl_UI_Book_CancelConfirm",
    "gbl_Book_SubmitResult"
  ],
```

This is the exact list from code-review H-3's recommendation, covering the wizard state vars set
(or intentionally re-prefilled) at every hand-duplicated reset site.

## Verify before applying the config change

Once `statefulVars` is populated, `node tools/pa-lint/lint.js` will require every one of the 14
vars above to appear (word-boundary match) somewhere in the same formula as each marker. Spot-check
performed during this batch:

- `home-book-tile`, `find-free-slot`, `rooms-free-slot`, `rooms-book-bar`, `mybookings-empty-book`:
  all 14 vars present in the marked formula (either reset to blank/Today or re-derived).
- `bookingdetail-change-time`: all 14 vars present — the site prefills `varSelectedRoom`,
  `varSelectedDate`, `varStartTime`, `varEndTime`, `varTitle` from the booking being edited rather
  than blanking them (times-only edit), but every var is still touched, so this site passes.
- `bookingdetail-fix-cycle-advance`: all 14 vars present in the same branch.
- Two sites (`rooms-free-slot`, `rooms-book-bar`) never `Set(varSelectedRoom, ...)` inside their
  own formula — Rooms already has a room selected via the browse/selection-bar flow before either
  button is reachable, so `varSelectedRoom` is set elsewhere before these sites run. If this list
  is applied as-is, both sites will fail L6 on `varSelectedRoom` even though the omission looks
  intentional from reading the surrounding screen. Recommend either scoping `varSelectedRoom` out
  of the vars required at those two specific markers (L6 currently applies the same var list to
  every marker — no per-site scoping exists) or confirming in Studio that room selection truly
  can't go stale across these two entry points before flipping this config on.
