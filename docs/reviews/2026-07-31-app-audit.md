## Executive summary

The app is architecturally better than most Canvas Apps — App.Formulas is used heavily and well (named formulas for all derived data, UDFs like `fnOverlaps`, a proper theme token system, `App.OnError` handler, every SharePoint `Patch` wrapped in `IfError`). The problems are concentrated in four cross-cutting patterns rather than scattered one-off mistakes:

1. **The `colBookings` snapshot is the single point of failure** (CRITICAL). Every clash check, series cancel, and series edit runs against an in-memory full-table copy of `Book_Bookings` that is (a) refreshed only at screen entry / after own mutations, so **concurrent users can double-book**, and (b) a non-delegable full pull that **silently truncates at the data-row limit**, so once the list grows past 500–2000 rows, clash checks miss bookings and series cancels skip occurrences while reporting success. ~19 separate `ClearCollect(colBookings, Book_Bookings)` sites re-pull the whole table after every mutation.
2. **The booking wizard's state contract is sprawl** (HIGH). ~17 app-globals form the implicit interface to `cpt_Modal_`; the reset block is copy-pasted at 7+ call sites (already drifting), close/discard paths don't fully clear state, and `cpt_BookingDetailModal` reaches directly into 15 of `cpt_Modal_`'s internal variables.
3. **Series operations have real logic holes** (HIGH): no ownership predicate on series cancel, a re-time path that can write an overlapping booking as `Active`, in-progress occurrences skipped by "whole series" cancel, and monthly recurrence that can land on weekends.
4. **Rooms-screen weight and the timeline algorithm** (HIGH perf + HIGH bugs): one screen hosts two full page trees (App Checker complexity 352 vs 300 threshold), and the timeline free-slot builder fragments free time by hour — which permanently disables the 90m/2h duration chips and can render phantom bookable slots.

Positives worth keeping: OnVisible handlers are mostly thin (Home's is a single `Set`), data shaping lives in named formulas, zero `Rectangle` Radius violations (the known compile-reject trap), zero naked Patches, soft-delete via `Status` everywhere (no destructive `Remove`).

## 1. BUGS

### CRITICAL

**BUG-1 — Clash detection runs on a stale local snapshot; concurrent double-booking is possible.**
Where: `cpt_Modal_.btnConfirm.OnSelect` (Components/cpt_Modal_.pa.yaml:1739–1747); host OnSubmit handlers Home.pa.yaml:1951–1960, Find.pa.yaml:697–706, Rooms.pa.yaml:1834–1843; `btnHDNextExtend` Home.pa.yaml:1097–1107.
`ClearCollect(colOverlappingBookings, Filter(colBookings, Status="Active", fnOverlaps(...)))` — the confirm-time re-check filters the in-memory `colBookings` with **no `Refresh(Book_Bookings)` before the check**. The "This slot was just taken" error (cpt_Modal_.pa.yaml:1518) cannot detect a slot just taken by another user. Two users pass validation simultaneously; the loser is written with `Status="Clash"` at best (host handlers do per-occurrence checks — also against the stale snapshot) or `Active` at worst.
Fix: immediately before the confirm-time check, do a scoped server re-read (`Filter(Book_Bookings, RoomID = …, StartDateTime < windowEnd, EndDateTime > windowStart)` into a small temp collection) and check against that. True atomicity needs a server-side guard (Power Automate / list validation), but a fresh scoped read closes 95% of the window.

**BUG-2 — `colBookings` full pull truncates at the data-row limit; mutations then operate on the missing rows' absence.**
Where: ~19 sites — App.pa.yaml:611 (OnStart), Home:1118/1157/2026, Find:13/772, myBookings:10/1340, bookingDetail:466/577/621/713/742/833, Rooms:14/1909, cpt_BookingDetailModal:770–783/855–868/893–916. Confirmed by App Checker (`CollectDelegatableDataSource`, 15 findings).
Once `Book_Bookings` exceeds the data-row limit (500 default / 2000 max), `colBookings` silently drops rows. Consequences compound: clash checks (BUG-1) miss bookings → double-books with no error; series cancel/edit loops (`Filter(colBookings, SeriesID = _sid, …)`) **skip occurrences beyond the cap while toasting "Series cancelled"** (myBookings:1326–1342, bookingDetail:733, cpt_BookingDetailModal:900).
Fix: bound the pull with a rolling window (e.g. `EndDateTime >= Today()-90 && StartDateTime <= Today()+180`) — every consumer already filters to windows narrower than that — and make series mutations delegable (`UpdateIf(Book_Bookings, SeriesID = _sid && …)`) or at minimum iterate a fresh server-side `Filter(Book_Bookings, SeriesID = _sid)`.

### HIGH

**BUG-3 — Series cancel has no ownership predicate.**
Where: bookingDetail.pa.yaml:733, myBookings.pa.yaml:1331, cpt_BookingDetailModal.pa.yaml:900.
`Filter(colBookings, SeriesID = _sid, StartDateTime >= Now(), Status <> "Cancelled")` — mutation set is ALL bookings sharing the SeriesID, with no `BookedByEmail = Lower(User().Email)`. Display galleries use the ownership-filtered `MyBookings` named formula; the mutations don't. Book-on-behalf exists (`varBookForEmail`), so cross-owner series membership is reachable. Defense-in-depth: add the ownership predicate to the mutation filter.

**BUG-4 — Re-timing "just this booking" onto a busy slot writes an overlapping `Active` booking.**
Where: bookingDetail.pa.yaml:564–573.
`Patch(... {StartDateTime: gbl_PendingStart, EndDateTime: gbl_PendingEnd, IsException: true, Status: If(_free, "Active", gblSelectedBooking.Status)})` — when the target slot is busy and the booking was `Active`, the row is **moved onto the occupied slot still marked `Active`** (two overlapping Actives), while the notify text claims it's "still clashed". Should be `If(_free, "Active", "Clash")`, or block like the standalone edit path (bookingDetail:806–818) does. Related: the follow-up "remaining clashes" check (bookingDetail:584–591) excludes the just-patched row, so the user can be told "All clashes resolved" while it is still clashed.

**BUG-5 — Rooms timeline fragments free runs by hour → 90m/2h chips permanently disabled; cross-hour booking impossible from the timeline.**
Where: Rooms.pa.yaml `btn_LoadTimeline.OnSelect` 1633–1710 (row builder), `btnTLFree.OnSelect` 1100 (`varTLSelRunEnd: ThisItem.RowEnd`), chips 1504/1532.
Free rows are emitted at most 60 minutes long (clipped to hour cells), so `DateAdd(varTLSelStart, 90) > varTLSelRunEnd` is always true → `btnTLChip90`/`btnTLChip120` can never enable, contradicting `MaxBookingMinutes = 240`. Fix: merge contiguous free segments when building `colTimelineRows`, or compute `varTLSelRunEnd` as the end of the contiguous free run.

**BUG-6 — Rooms timeline gap algorithm can render phantom "free" rows over active bookings.**
Where: Rooms.pa.yaml:1671–1706.
The next-booking lookup only considers bookings starting at/after the current booking's end; a longer booking that started earlier and is still running is invisible to it (e.g. A 09:00–09:30 + B 09:00–10:00 both Active → free row 09:30–10:00 rendered over B). Normally masked because overlaps are stored as `Status="Clash"` and filtered out (Rooms:1609), but any concurrently-created Active overlap (BUG-1) renders a bookable phantom slot.

**BUG-7 — Past slots are selectable and bookable from the Rooms timeline.**
Where: Rooms.pa.yaml `btnTLFree.OnSelect`:1082–1110 (past-slot fallback `_start = _slotStart`), `cpt_Modal_` validates weekend + clash + past only for occurrence 1 at the confirm gate — but the timeline pre-fill path with a fully-past slot sets a past `varStartTime`, and `btnNext.DisplayMode` (cpt_Modal_:1693) omits `fnIsPast`, so the user discovers the block only at step 3 (or not at all if the gate is bypassed by an edit path).
Fix: disable `btnTLFree` for `fnIsPast(ThisItem.RowEnd)` rows and add `fnIsPast` to `btnNext.DisplayMode`.

**BUG-8 — App-level named formulas depend on variables first set on the Find screen.**
Where: App.pa.yaml:334–340 (`varFindWindowStart/End`, `varFindWeekStart`, `WeekBookings`); setters only in Find.pa.yaml:7–8/66/88/97/641–642.
`varFindSelectedDate`/`varFindViewMode` are not seeded in App.OnStart, so `DateValue(Text(Blank()))` poisons `FindBookings`/`WeekBookings` until Find's first OnVisible. Today all consumers happen to live on Find and evaluate after OnVisible's Sets, so it's latent — but any new consumer (a Home "this week" card, for instance) silently gets errors/blank.
Fix: seed both in App.OnStart, or make the formulas defensive: `Coalesce(varFindSelectedDate, Today())`.

**BUG-9 — Series-cancel success toast fires regardless of per-occurrence failures.**
Where: cpt_BookingDetailModal.pa.yaml:893–916 (also pattern at myBookings:1326–1342).
Each `Patch` in the `ForAll` is IfError-wrapped, but the result table is discarded and `Notify("Series cancelled", Success)` runs unconditionally. Partial failure → N error toasts, then a success toast, modal closes. Fix: collect failures (the Home OnSubmit pattern, Home:1997–2012, does this correctly) and branch the notify.

**BUG-10 — Recurrence integrity gaps in the wizard.**
Where: cpt_Modal_.pa.yaml:1782–1829.
(a) Occurrences 2..N are never conflict-checked client-side — hosts catch them at Patch time and write `Status="Clash"` (by design per the fix-cycle), but the user gets a "success with warnings" outcome for clashes that were knowable pre-submit. (b) Monthly recurrence `DateAdd(varStartTime, _occ.Value-1, TimeUnit.Months)` can land on weekends — the Mon–Fri rule is enforced only for occurrence 1 (cpt_Modal_:467/509/1693). (c) `Status` outcome for clash branch is reported to the host as `"success"` (Rooms:1914–1917).

**BUG-11 — Self-referential ClearCollect in the Find grid builder.**
Where: Find.pa.yaml:206.
`ClearCollect(colFindRows, SortByColumns(colFindRows, …))` — clearing a collection while lazily reading it is an undefined pattern; can intermittently produce an empty/partial grid. Sort into a temp collection, or sort at the consuming gallery instead.

**BUG-12 — Find free-gap derivation assumes `FindBookings` is chronologically sorted; it isn't guaranteed.**
Where: Find.pa.yaml:185–201 vs the sort happening after gap derivation (line 206).
`First(room)` / `LookUp(room, StartDateTime >= b.EndDateTime)` return first-in-table-order, not earliest. `FindBookings` (App.pa.yaml:418–436) sorts by StartDateTime — **but** the gap pass runs on a `Filter` of it and `LookUp` order guarantees are weak; and Clash rows are excluded upstream while overlapping Actives (BUG-1 aftermath) corrupt the gap chain. Derive gaps from an explicitly sorted table.

**BUG-13 — Wizard state not cleared on close/discard; stale data leaks into the next booking.**
Where: cpt_Modal_.pa.yaml `scrimBackdrop.OnSelect`:61–77, `btnBack`:1598–1617, `btnClose`:1648–1664, `btnDiscardBooking`:1938–1950.
None of the close paths clear `varTitle`, `varSelectedRoom`, `varStartTime/EndTime`, `varSelectedDate`, `varConflict`, or `gbl_UI_Book_Modal_Step` (`Reset(txtBookingTitle)` resets to `Default: =varTitle` — the stale value). Every host open-site must re-seed all ~17 vars, which is exactly why the reset block is copy-pasted 7 times (STATE-2). A discarded edit's room/time/title reappear if any open path misses a var, and the modal can reopen on step 2/3.

## 2. PERFORMANCE

### The load model today

App.OnStart: 14 `Set`s + 2 full-table `ClearCollect`s (`colRooms`, `colBookings`) + mock seeds — **sequential, no `Concurrent()`** (App.pa.yaml:590–620). Every screen entry to Find/myBookings/Rooms then re-runs `Refresh(Book_Bookings)` + full `ClearCollect` again before the screen is interactive, and every mutation re-pulls the full table once more. Home's OnVisible is a single `Set` — the pattern the other screens should follow.

**PERF-1 (HIGH) — ~19 full-table pulls of `Book_Bookings`.** The dominant cost and also BUG-2. After any cancel/extend/submit, the entire list is re-downloaded to update one row. Fix: `Patch` the changed row(s) into `colBookings` locally after a successful server write (or re-collect a narrow window). This one change removes most network weight from every mutation path in the app.

**PERF-2 (HIGH) — App.OnStart is sequential.** Wrap the two big collects in `Concurrent(ClearCollect(colRooms, …), ClearCollect(colBookings, …))`; seed the trivial `Set`s first. With a bounded `colBookings` window (BUG-2 fix) startup pulls shrink further. The mock seeds (`colUserSettings`, `colPeople`) are microscopic — fine — but note they run in production (`PROD-REVERT` markers present; see UX log).

**PERF-3 (HIGH) — Rooms screen hosts two full page trees.** Browse (~31 controls) + timeline (~61) coexist behind `varShowTimeline` (Rooms:77/592); the hidden tree still binds all formulas and counts toward the 352 complexity score. **Splitting the timeline into its own screen is the single biggest lever** (≈ −60 complexity, below threshold) and matches the App Checker's own recommendation.

**PERF-4 (HIGH) — Nested galleries with per-row LookUps re-evaluated on every tick.**
- Rooms browse tiles: `gal_rooms_view` template = 14 controls incl. 2 nested galleries; `galRoomsAvailabilitySegments` runs ~20 `LookUp`s per tile per re-evaluation (Rooms:370–401) — ~240 LookUps for 12 visible tiles, re-run whenever `varNowTick`/data changes. Fix: precompute a per-room slot table/string in `RoomsBrowseBase` (it already does one Filter per room) or render the strip as a single generated-SVG Image per tile.
- Home occupancy: `galHDOccSegments` nested in `galHDOccRooms` — rooms × 20 slot rectangles, each with a `LookUp` (Home:1748–1797). Same fix shape: precompute per-slot state into `RoomOccupancyToday`.
- Find timeline: `galFindColRows` (flexible-height, the most expensive gallery variant) nested per room column, `Items = Filter(colFindRows, RoomKey = ThisItem.ID)` re-filtered per column per redraw (Find:413–440), template carries all three row-type branches (8 controls, ≤4 visible) (Find:442–657).

**PERF-5 (MEDIUM) — Find's rebuild-everything interaction path.** Every date arrow, tab change, and filter change re-runs `Select(btnLoadFindBookings)`: triple-nested `ForAll`+`Collect` grid build, self-referential re-sort, and in Week mode a second nested pass with per-cell `Filter`+`Sum` (Find:160–246). Combined with OnVisible's `Refresh`+full pull, this is the heaviest interaction path in the app. The `ForAll`-with-`Collect` pattern (also Rooms:1618–1710, and all OnSubmit handlers) is App-Checker-flagged 8×: batch instead — `Collect(target, ForAll(src, {…}))` — one change notification instead of one per row.

**PERF-6 (MEDIUM) — Submit path does N+1 server round-trips.** Sequential per-occurrence `Patch` inside `ForAll` (+ per-row `LookUp(Book_Bookings, ID = …)` in series cancel = N+1 reads), then a full re-pull, then a full grid rebuild (Find:692–806, Rooms:1829–1909, cpt_BookingDetailModal:893–916). Batch: single `Patch(Book_Bookings, ForAll(colPayloadOut, {…}))` where shapes allow, or at least drop the full re-pull (PERF-1).

**PERF-7 (MEDIUM) — Duplicated expensive expressions that belong in named formulas.**
- "Rooms free now" O(rooms × bookings) expression duplicated verbatim (Home:136 and 455–468) → `FreeNowCount` named formula.
- The 40-line availability/alternative-rooms block duplicated ×4 inside cpt_Modal_ (292–331, 585–633, 711–758, 1738–1776) — each dropdown change re-runs an O(rooms × overlaps) cross-join → one UDF or output-driven recompute.
- Tab counts `CountRows(Filter(MyBookings, …))` ×4 incl. a GroupBy (myBookings:220/433/494/555); `mb2GalSeries.Items` runs Sort-inside-Filter per group on every re-collect (myBookings:1118–1136).
- Same `LookUp` computed twice for status dot + status text (Rooms:1276/1291).

**PERF-8 (MEDIUM) — HtmlViewers in the shell.** Shell_Header carries 2 HtmlViewers (wordmark + avatar initials) × every screen instance; Profile adds a third for a static initials circle (Profile:97–107). HtmlViewer is one of the heaviest controls; a Label in a circular container does the same job. Also `htxProfileAvatar` hardcodes font/colors outside the token system.

**PERF-9 (LOW-MEDIUM) — Classic control estate.** 77 Classic/Buttons (each carrying ~8-way hover/pressed color formula blocks — ~40 formulas just in Rooms' four copy-pasted duration chips, Rooms:1439–1550), Classic DropDowns/TextInputs. The chips alone could be one 4-item gallery. Migration to modern controls is a bulk refactor — sequence it after the structural fixes; the immediate win is collapsing the copy-paste chip/button blocks.

**PERF-10 (LOW) — Structural filler.** ~35 Rectangles + a set of spacer Labels/containers used purely as dividers/underline/legend swatches (14 on myBookings alone); container borders replace most. `galRooms` in the wizard renders all rows (Height = full content, `ShowScrollbar: false` — no virtualization). SVG data-URI button faces via `ButtonProperties`/`TileProperties`: confined to the wizard's room tiles (regenerated for all tiles on each selection, cpt_Modal_:251–269) and two static date arrows — not the app-wide cost it could have been (Home uses none).

### Findings

**STATE-1 (HIGH) — The wizard contract is ~17 implicit globals with 7+ copy-pasted reset sites.**
Home:290–349 & 1225–1257, myBookings:611–645 & 1070–1104, Rooms:1566–1583 & 1796–1813, Find:510–564, bookingDetail:311–336. The blocks are already diverging (the timeline site seeds times, others blank them). Combined with BUG-13 (close paths don't clean up), correctness depends on every current and future open-site remembering ~17 `Set`s. Fix: one `fnOpenBookingWizard(room, date, start, end, editId)` UDF in App.Formulas (the app already uses UDFs) — collapses 7 sites to 7 one-liners and makes BUG-13 moot.

**STATE-2 (HIGH) — Components write app globals freely; one component reaches into another's private state.**
All three components have `AccessAppScope: true`. Shell_Header navigates and writes 4 globals from inside the component; cpt_BookingDetailModal owns no custom properties at all (100% global-coupled) and `bdmBtnChangeTime` (cpt_BookingDetailModal:644–674) sets **15 of cpt_Modal_'s internal variables** — the single worst coupling site in the app. Any rename inside cpt_Modal_ silently breaks a different component. Fix direction: route cross-component choreography through host-screen handlers or component Input/Output properties (the `PatchPayload` output pattern already in cpt_Modal_ is the model to follow).

**STATE-3 (MEDIUM) — Stale-on-revisit state.**
- `gbl_UI_CancelSeriesConfirmID` survives navigation: leave myBookings mid-confirmation, return → the destructive "Yes, cancel series" is pre-armed (myBookings has no OnVisible reset).
- `gbl_UI_Detail_Modal` left true reopens the modal on revisit; `gbl_SelectedSeriesID` keeps a row expanded.
- `gbl_FixCycleSeriesID` cleared only on bookingDetail's own exit paths — leaving via the shell header keeps fix-cycle armed for a later unrelated edit.
- `gblEditingBookingID` reset to 0 only on specific open paths; a stale non-zero ID from an abandoned edit changes the semantics of the next `OnSubmitEdit`/`ID <> gblEditingBookingID` clash exclusion.
- Rooms resets filters/search/timeline on every entry (state loss — opposite problem, see UX log) while myBookings resets nothing — no consistent revisit policy. Find resets date/view but not capacity/equipment.
- Submit bookkeeping (`colPayloadSnapshot`, `colFailedBookings`, `varNewSeriesID`) lingers app-lifetime after success.

**STATE-4 (MEDIUM) — Naming convention chaos undermines auditability.** Four prefixes in live use (`glb`, `gbl`, `gbl_`, `var`) with near-collision pairs: `glbSelectedDate` (Rooms timeline date) vs `varSelectedDate` (wizard date) vs `varFindSelectedDate` (Find date) — three date globals whose roles are only distinguishable by reading call sites; `varAlternativeRooms` is a collection; `varShowTimeline`/`varConfirmCancel` are context vars while every other `var*` is global. No bug found from the near-collisions today (the wizard consistently reads `varSelectedDate`), but this is the highest-leverage refactor for preventing the next one. Convention proposal: `gbl*` globals / `ctx*` context / `col*` collections, one date-variable per concern.

**STATE-5 (LOW) — Dead/duplicated state.** Unused component inputs (`HeaderNavTab`, `InstanceScreenName`, `ModalTitleText`, `OptionalLabelText`) fed placeholder values by every instance; `varBookingError` doubles as wizard-reset flag and submit outcome; `gbl_Book_SubmitResult`/`varBookingError` written by hosts, read by component — a two-variable channel where one would do; `IsSandbox = false` named formula plus live mock seeds (`colUserSettings`, `colPeople`) in production OnStart — consistent with the PROD-REVERT contract, but the settings UI reads/writes mock data in prod (see UX log).

**STATE-6 (POSITIVE) — What's right.** Derived data is uniformly in named formulas (`MyBookings`, `RoomsBrowseData`, `RoomOccupancyToday`, …) rather than snapshot collections — the App Checker's `CollectingReadOnlyTable` hits (4) are the exceptions (`colPeople`, `colUserSettings`, `varAlternativeRooms`, `colSeriesEditPlan`) and are minor. `varNowTick`-instead-of-`Now()` is a deliberate, documented recalc-control pattern. `UpdateContext` is used correctly where it's used. `PatchPayload` output-property snapshot in cpt_Modal_ documents and fixes a real race.
